# Infra Scaling — Paid GPU Options for Full-Dataset CUAD Runs

## Why

`Retrieval_Strategy.md` (Step N) and `evaluation/cuad_trials.md` (Exp N @ N=100) found that
metrics don't stabilize at N=20 — Exp N's relevance/utilization collapsed when scaled to N=100.
That means the current experiment rankings (E–P, all at N=20) may not hold at the full ~1530-sample
CUAD dataset. Re-validating past experiments — and trying further improvements — at full scale
means running 10+ experiments at N~1500 each.

**Local timing is too slow for that.** Measured in `notebooks/03_cuad_rag_scale.ipynb` (Exp N,
N=100, local Ollama on Apple Silicon):

- Generation (retrieval + generator LLM): 39.2s/sample → ~16.7 hr for N=1500
- Judge (TRACe eval): 19.0s/sample → ~8.1 hr for N=1500
- **Total: ~24.7 hr per run → ~247 hr (~10 days) for 10 runs**

## Decision — first step

Before committing to a paid batch, benchmark actual T4 throughput using **Experiment N's exact
model set** (embedder=`nomic-embed-text-v2-moe`, generator=`mistral-small3.2:24b`,
judge/HyDE=`llama3.1:8b-instruct-q4_K_M`), at a small N (20) — see
`notebooks/04_cuad_rag_t4_benchmark.ipynb`.

Holding the model set fixed isolates one variable: **does the T4 GPU alone speed things up enough
to matter, independent of which models we ultimately pick.** The model set is *not* locked in for
the real 10-run batch — once we know which infra tier to use, we're free to pick different/cheaper/
faster models per platform (e.g. Groq for the judge role). A "T4 isn't fast enough" result should be
read as "not fast enough for `mistral-small3.2:24b` specifically," not as a verdict on T4 in general.

`mistral-small3.2:24b` at q4 quantization is a tight fit in T4's 16GB VRAM — the benchmark should
watch for OOM as well as raw per-sample timing.
